## Summary of Changes

### Root Cause of the Compilation Failure

The core blocker was that `ExteriorTurn` in `SpectreGeometry.lean` only derived `DecidableEq, Repr` — NOT `BEq`. This meant `==` on `ExteriorTurn` was routed through `instBEqOfDecidableEq`, which wraps `Decidable.rec`. Neither `dsimp only`, `simp only`, nor `decide` could reduce expressions like `ExteriorTurn.t_minus_90 == ExteriorTurn.t_90` to `false` because the `Decidable.rec` projection was opaque to all those tactics.

### Fix 1: `SpectreGeometry.lean`
Added `BEq` to `ExteriorTurn`'s `deriving` clause:
```lean
deriving Repr, DecidableEq, BEq
```
With `BEq` derived directly, `==` on concrete constructors becomes definitionally `true`/`false` via `rfl`.

### Fix 2: `SpectreBoundary.lean` — `foldl_add_distrib`
- Base case: `rfl` → `simp [List.foldl_nil]` (fold on nil isn't definitional enough for `rfl` across the `+0`)
- Cons case: the key insight was to use `ih (0 + d)`, then `rw [h3]` (where `h3 : 0 + d = d` by `omega`) to normalize the argument, then close with `omega` using `h1` and `h2`.

## Key Technical Lesson

**`BEq` vs `DecidableEq`-derived `BEq`**: When `inductive T deriving DecidableEq` is used, the `==` operator is `instBEqOfDecidableEq.1` which is a **projected typeclass instance** that goes through `Decidable.rec`. This is **not definitionally equal** to `true`/`false` on concrete constructors — it requires kernel reduction that simp/dsimp/decide don't trigger. The correct fix is `deriving BEq` which generates a structural match returning `Bool` directly, making concrete `==` calls definitionally true/false via `rfl`.
